# Feeding TrackingOpsControl real data

The app reads **datasets**: folders under `public/data/<name>/`. Pick one with the **Data** menu in the header, or with `?data=<name>` in the URL. Two ship with the project:

| Dataset | What it is |
|---|---|
| `demo` | The full error scenario: cameras down, a cleared outage with affected pitches, session OUT, BDS down, failed tasks, and one alert that arrives 8 s after load. |
| `healthy` | Everything at full health. Use it while tweaking layout. |

Both are generated by `node scripts/make-demo-data.mjs`. You don't need the script for real data.

## Add a real dataset

1. Copy `public/data/demo` to `public/data/<your-name>` (for example `game-823476`).
2. Replace the JSON files with real values (formats below), and drop images into `images/`.
3. Add the name to `public/data/index.json` so it shows in the Data menu.
4. Open `http://localhost:5173/?data=<your-name>`.

Anything you leave out falls back to sensible defaults, so you can grow a dataset one file at a time. Start with `cameras.json` and some images.

The exact contract is `src/data/types.ts`. It's the source of truth, and TypeScript will flag mismatches as you edit the app.

## Folder layout

```
public/data/<name>/
  game.json        venue, GamePK / Session ID, game mode, session, clock (now, date), redundancy, timing, thresholds, default images
  cameras.json     every camera (PitchToPlate 1-6, FullField 1-8, Biomechanics 1-16)
  pitches.json     every pitch, oldest first: confidence, strike zone, PP results, cloud state, per-pitch images
  status.json      raw BMCC / BMCA status-box lines; the app turns these into alerts
  images/
    default/       fallbacks: live.jpg, tracking.png, mosaic.jpg, still.jpg, spin-strip.png (hit.jpg optional)
    cameras/P1/    live.jpg, tracking.png, mosaic.jpg ...        (referenced from cameras.json)
    pitches/32/    P1-mosaic.jpg, P1-hit.jpg ...                 (referenced from pitches.json)
```

All image paths in the JSON are **relative to the dataset folder**, for example `"images/cameras/P1/live.jpg"`.

## Images: which comes from where

| Where it shows | Field | Fallback |
|---|---|---|
| Cameras › Control live image | `cameras[].images.live` | `game.defaultImages.live` |
| Cameras › Monitoring › Tracking window | `cameras[].images.tracking` | `defaultImages.tracking` |
| Cameras › Monitoring › Monitored image (bio) | `cameras[].images.still` | `defaultImages.still` |
| Ball mosaic (Game grids, Monitoring) | `pitches[].images[camId].mosaic` | `cameras[].images.mosaic`, then `defaultImages.mosaic` |
| Hit image (Game grids) | `pitches[].images[camId].hit` | `defaultImages.hit`, else a placeholder |
| Post-processing spin strip | `pitches[].spinStrip` | `defaultImages.spinStrip` |

Calibration overlays are drawn **on top** of the live image from `cameras[].calibration` (`imageSize`, `lines`, `keyPoints`, all in the live image's pixel space). Use images **without** BMCA's baked-in overlay if you can, so the overlay toggles and nudging look right.

## Times

Every time in a dataset (`game.now`, `pitches[].time`, `status[].at` / `clearedAt`) can be either:

- **A full timestamp** (preferred): `"2026-11-04T05:09:34.206Z"`. A timestamp with no zone is read as UTC.
- **A clock time**: `"05:09:34"` or BMCC's `"05-09-34.206"`. Give `game.date` (the UTC date of `game.now`, e.g. `"2026-11-04"`) alongside a clock-only `now`.

A clock time has no date, so the app reads it as **the latest moment with that clock time at or before `game.now`** (with a minute's grace). Everything in a dataset has already happened by `now`, so a game that crosses midnight works: with `now` = `00:40:00`, a pitch at `23:58:10` belongs to the previous day. This matters because BMCC times look like UTC, and evening games in the Eastern and Central time zones cross 00:00 UTC.

If a converter can produce full timestamps, prefer them: a dataset that spans more than 24 hours only works with full timestamps.

## cameras.json

```jsonc
{
  "id": "P1",                       // stable id used everywhere (P1-P6, F1-F8, B1-B16)
  "group": "pitchToPlate",          // pitchToPlate | fullField | biomechanics
  "number": 1,
  "bmccTrackingNumber": 1,          // BMCC tracking camera 1-14 (P2P 1-6, FF 7-14); omit for biomechanics
  "host": "BMCA1",                  // BMCA host: matches status-message sources, used by "Open in BMCA"
  "bmccName": "Camera 15",          // biomechanics only: the name BMCC shows in the monitored-camera list
  "running": true, "fps": 600, "targetFps": 600,
  "tracking": { "multicamPresent": true, "playerTracking": true },   // P2P/FF only
  "images": { "live": "images/cameras/P1/live.jpg" },
  "calibration": { "imageSize": [1920, 1080], "lines": [[x1, y1, x2, y2]], "keyPoints": [{ "id": "hp", "label": "Home plate", "x": 0, "y": 0 }] },
  "settings": { "expTarget": 80, "aGain": 30, "focus": 14028 },     // current BMCA values; anything omitted uses the defaults
  "lastBall": { "strength": 7, "perimeter": 62.4, "area": 288, "boxes": [{ "x": 48, "y": 280, "size": 34 }] },
  "antiwobble": { "linesMatched": 14, "linesTotal": 14, "patchesMatched": 8, "patchesTotal": 8 }
}
```

Health comes from these fields alone: **not running → crit**, **fps below target → warn**, **missing from multicam / player tracking skipped → warn**.

## pitches.json

```jsonc
{
  "num": 32, "time": "05-09-58.206",          // full timestamp, or BMCC "HH-MM-SS.mmm" / "HH:MM:SS" (see Times)
  "confidence": 8.57, "trackLength": 10.0, "trackQuality": 5.91, "acsDelivered": true,
  "hit": { "trackPct": 100, "distanceFt": 120.5 },                    // or null
  "strikeZone": { "P1": 0.000, "P6": null, "F2": 0.007 },             // Δ per tracking camera; null = no data
  "pp": {
    "release":  { "status": "success", "mph": 97.6 },                 // success | failed
    "spin":     { "status": "success", "rpm": 2564.7, "fitError": 0.20 },
    "trackpac": { "status": "valid" }                                  // valid | validation_failed | failed
  },
  "cloud": { "trackpac": "uploaded", "bat": "success", "pitcherBiomech": "success", "batterBiomech": "failed" },
  "images": { "P1": { "mosaic": "images/pitches/32/P1-mosaic.jpg", "hit": "images/pitches/32/P1-hit.jpg" } }
}
```

Cloud states: Trackpac `queued | processing | successful | needs_validation | uploaded | failed`; cloud tasks `queued | processing | success | failed`.

## status.json: raw messages become alerts

Paste status-box lines as they are. **Don't write alerts by hand.** `src/alerts/engine.ts` matches each message against rules, and each rule knows which camera the message is about and where in the UI it gets fixed:

```jsonc
{ "at": "05:09:34", "level": "CRITICAL ERROR", "source": "BMCC",
  "text": "Cameras:: \"6 Missing from multicam frames, ensure software is launched and running at full frame rate.\"" }
{ "at": "04:47:14", "clearedAt": "04:49:04", "level": "CRITICAL ERROR", "source": "BMCC", "text": "Cameras:: \"11 Missing ...\"" }
```

| Message pattern | Becomes | Routes to |
|---|---|---|
| `Cameras:: "N Missing from multicam frames"` | CRIT "[camera] not running" (by `bmccTrackingNumber`) | Cameras › that camera |
| …the same with `clearedAt` | Cleared CRIT; the pitches in that time window are flagged as affected | Post-processing › affected pitches |
| `Monitored Cameras: BMCAnn … red` | CRIT "[camera] not running" (by `host` / `bmccName`) | Cameras › that camera |
| `… Not done on: 5 …` (player tracking) | WARN "Player tracking skipped on [camera]" | Cameras › that camera |
| `Antiwobble Consensus: … Not enough successful patches` (source `BMCAn`) | WARN "Antiwobble falling back on [camera]" | Cameras › Control › Calibration |
| `Writing to disk disabled` | Developer message | (hidden unless Developer is on) |
| anything else | Developer message, so new message types show up for triage | |

The app also raises alerts straight from the data: camera not running, cameras below full frame rate, session not In while LIVE, BDS not connected, timing over threshold, cloud tasks failed, and spin fit error over the review line.

`appearsAfterSec` (demo only) holds a message back for N seconds, to show an alert arriving mid-session.

## Alert lifecycle (the ledger)

The engine only says what is wrong *now*. `src/alerts/ledger.ts` keeps every **occurrence** of a problem, so operators see a proper lifecycle:

| What happens | Result |
|---|---|
| A problem appears | New alert (notifies if its rule says so) |
| It goes away before anyone acknowledges it | Stays open as **CLEARED · NOT ACKNOWLEDGED** |
| It comes back while still unacknowledged | The same alert reopens (no duplicate) |
| It comes back after being acknowledged | A **new** alert, so it isn't hidden by the old acknowledgement |
| A grouped alert (cameras below full rate, cloud tasks failed, spin fit error) gains a member after being acknowledged | A **new** alert; the old one shows "Replaced by a newer alert" |
| A member recovers and then drops again (for example a camera falls below full rate a second time) | Counts as gaining a member: a **new** alert if acknowledged, otherwise the open one notifies again |
| A cleared, unacknowledged alert comes back | Reopens and notifies again, even if its notification had been hidden |

Status messages are one occurrence per message (keyed on what they're about plus their start time) and keep their own `at` / `clearedAt`. Alerts derived from the data use the time the app first saw them. Conditions already present when the app starts show "Active" with no duration, because their start is unknown.

To try it in the demo: repush the failed cloud tasks or reprocess the flagged spin pitches, and those alerts move to cleared-not-acknowledged instead of disappearing.

## Converting real exports

If BMCC/BMCA give you logs or CSVs, write a small converter script in `scripts/` that turns them into these four files. Keep the converter out of `src/` so the app only ever sees the contract above.
